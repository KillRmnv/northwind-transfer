# LIMITS

Честные границы решения. Обновляется каждые несколько часов работы.

## L1. Реализовано на текущий момент

Level 1–2 и большая часть Level 3: котировки (`SOURCE`/`TARGET`, `charged_in=TARGET`, minor_units 0/2/3), переводы с идемпотентностью, резервами, цепочкой провайдеров и проверкой неизвестного итога, вебхуки с HMAC и монотонностью, фоновая сверка, лимиты (суточный + определения с окнами и весом), миграции, сидер, 67 тестов, структурированные логи с маскировкой секретов, мапперы DTO.

Chaos-прогон 300 переводов (`--seed 11 --concurrency 10`): **`RESULT: OK`** — 275 `COMPLETED`, 25 `FAILED` (необслуживаемое направление и маржа ниже минимума), 38 двойных сабмитов; 0 двойных выплат, 0 зависших резервов/переводов, 0 расхождений баланса, 0 ошибок API. Длительность 270 с.

## L2. Что сломается первым

- Строгая HMAC-проверка (D10) против chaos-эмулятора без подписи — массовые `401`, переводы зависнут в `PROCESSING` до сверки. См. A8.
- `work_mem 16MB × 100` параллельных при маленьком контейнере — давление на RAM; без `shm_size: 1gb` параллельные запросы упрутся в `/dev/shm`.
- MySQL-профиль: `FOR UPDATE SKIP LOCKED` и `NUMERIC(20, 8)` ведут себя иначе чем в PG — нагрузочные тесты под MySQL могут потребовать отдельных настроек.
- Скользящие окна без таблицы счётчиков — агрегаты по `transfers` дорожают с ростом таблицы; партиционирование не заложено.

## L3. Компромиссы

- Сверка — поллингом, не CDC/очередью: проще, но задержка до N минут.
- Single-runner сверки через `SKIP LOCKED`, без распределённых локов типа ShedLock.
- `sqlite`-профиль — только для локального прогона, конкурентные гарантии на нём не проверяются.

## L4. Схема: что сломается первым

- Агрегаты скользящих окон считаются по `transfers` без таблицы счётчиков — с ростом таблицы запросы за 16-дневное окно дорожают; партиционирования по `created_at` нет.
- Веер из 8 FK от `Валют` усложняет чтение диаграммы и планирование джойнов; при росте числа сущностей с валютой понадобится вынести валютные правила в отдельный модуль.
- Естественные ключи справочников: переименование кода — миграция с каскадом, а не точечная правка.

## L5. Стартовый набор

- `mock_provider/` — вендорный код, под наши линты и стиль не подпадает; баги в нём правим только если блокируют проверку.
- Наш фильтр провайдеров строже мока (мок терпит ±10% к лимитам) — расхождение осознанное, см. D7.
- Направление `RU-PH-CASH` (`CASH_PICKUP`) не обслуживает ни один провайдер из `providers.json` — котировка выдаётся, перевод честно завершается `FAILED` без попыток. Это данные задания, а не баг.
- Мелкие суммы на `RU-TH-CARD` (605–905 RUB) упираются в минимальную комиссию 80 RUB, маржа ниже `min_margin_percent` → `FAILED` без отправки денег по D7.
- `FAILED` без попыток — ожидаемое поведение только в этих двух случаях; любая другая причина означает баг фильтра провайдеров (проверять `payout_attempts`).
- `chaos_run.py` включает в план направления, у которых нет провайдера: он проверяет только `POST /quotes`, а не доступность выплаты.
- `payment-stack-starter` не используется; его инфраструктура (Vault, RabbitMQ, nginx, prometheus) в решение не входит.
- `chaos_run.py` — stdlib, внешних зависимостей нет; проверяет наш API целиком, поэтому зелёный прогон возможен только после Level 2-3.
