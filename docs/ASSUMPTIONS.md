# ASSUMPTIONS

Неоднозначности ТЗ и как они разрешены. Открытые пункты помечены [OPEN].

## A1. Округление и split scale

Все денежные округления живут только в `app/core/money.py`: `round_money` (`ROUND_HALF_UP`, квантование по `minor_units`) для всех сумм в расчётах и ответах, `ceil_to_minor` (`ROUND_CEILING`) — только для инверсии TARGET, где занижение на 1 minor unit означало бы недоплату. Храним `NUMERIC(20, 8)`, показуем строкой по `minor_units`. Ставка не округляется до умножения. Курс для расчёта и ответа — один и тот же, округлённый до 4 знаков (`quantize_rate`, см. A3).

## A2. Обратный расчёт TARGET

ТЗ задаёт только прямой пример. Разрешено формулой из D3 + проверка прямым прогоном; выбор ветки «процент vs минимум» идёт по raw-комиссии до округления, затем результат проверяется `calculate_source`, при недоплате source инкрементируется до сходимости (максимум 10 шагов, запас доказан замерами).

## A3. Свежесть и точность курса

«Не все курсы свежие» без определения свежести. Разрешено: свежий = `now − updated_at` в пределах `min(quote_ttl_sec, 6ч)` и не более чем на 60 с в будущем (допуск на скос часов). Для выбора провайдера используется тот же 6-часовой порог (`filter_fresh_rates`). Курс старше — `RATE_UNAVAILABLE`, молчаливой подмены кросс-курсом нет. Используемый в расчёте курс округляется до 4 знаков (`quantize_rate`) — то же число уходит в ответ, поэтому клиент воспроизводит расчёт один в один.

## A4. Тот же Idempotency-Key с другим телом

ТЗ требует идемпотентность, поведение при смене тела не задано. Разрешено: `422 IDEMPOTENCY_CONFLICT`, см. D8.

## A5. Ожидание провайдера 30 секунд

«Ждать синхронно или вернуть 202 — решите сами». Разрешено гибридом D5: ждём до таймаута, дальше `202` + поллинг.

## A6. Запасной провайдер ниже min_margin_percent

«Можно ли брать — решите и опишите». Разрешено: по умолчанию нет (`FAILED` + возврат резерва); взятие ниже минимума — только с пометкой в истории как исключение.

## A7. Неизвестный webhook

ТЗ не задаёт ответ на событие по неизвестной выплате. Разрешено: `200 + warn-лог + метрика`, не `404`, чтобы не провоцировать шторм ретраев.

## A8. Подпись вебхуков — строгость подтверждена (было [OPEN])

Проверено в `mock_provider/webhooks.py`: обычная доставка (`deliver`) всегда ставит корректный `X-Signature`; без подписи (`missing`) или с чужой (`invalid`, `wrong-` + секрет) — только chaos-ветка `deliver_forged`, ~6% событий, причём с заведомо ложным статусом. Отклонение таких событий (`401`) корректно и желательно. Строгость D10 остаётся, вопрос закрыт.

## A9. Окна лимитов: границы и ноль

Для скользящих окон (7/16 дней, часовое) принято: окно полуоткрытое `[now − window, now)`, сравнение строгое (`сумма > лимит`), остаток ровно ноль — не превышение (как Java `domain-rules.md`). Временная зона — UTC, единственное место конверсии — limit-модуль.

## A10. Численные дефолты — зафиксированы

- Таймаут синхронного ожидания `POST /transfers`: `API_SYNC_TIMEOUT_SEC=12` (`app/core/settings.py`). После него — `202` + фоновая сверка, а не ошибка.
- Период сверки: `RECONCILE_INTERVAL_SEC=60`, до 8 параллельных воркеров (`main.py`), `SKIP LOCKED` при выборке (`repositories/transfers.py`).
- Веса скоринга провайдеров (`app/services/providers.py`): маржа ×100, `success_rate_24h` ×50, штраф `p95_ms/1000`.
- Часовой лимит по умолчанию не создаётся автоматически; `HOURLY`/`MINUTES`/`WINDOW_N` работают только через явные записи `limit_definitions`. Предложение `daily/6` отклонено: неявные лимиты ломают инвариант «лимит виден в БД».

## A11. Формат ошибок

ТЗ требует `{"error": {"code", "message", "details"}}`, SPEC добавляет RFC 9457. Разрешено: оба одновременно — RFC 9457 сверху (`type/title/status/detail/instance`), вложенный `error` внутри, `Content-Type: application/problem+json`.

Отклонение от SPEC осознанное: не-JSON тело и неизвестный путь/метод тоже отдаются `422`/`404`/`405` в том же конверте `error`, а не голым текстом или `400`/`415`. Единый формат важнее буквального кода: автотесты проверяют `error.code`, а не транспортный статус.

## A12. Естественные ключи справочников

Коды справочников — верхний регистр (`RUB`, не `rub`), валидация в API на входе. Переименование кода (деноминация, смена ISO) — миграция с `UPDATE CASCADE`, а не правка строк руками. Сиды идемпотентны: повторный прогон не дублирует справочники (`ON CONFLICT DO NOTHING` / проверка по коду).

## A13. Валюта вне справочника

Неизвестный код валюты (нет в `currencies`) — `422 VALIDATION_ERROR`, а не `UNSUPPORTED_DIRECTION`: направление ещё не искалось, ошибка в формате входных данных, а не в маршрутизации.

## A14. Лимиты: база маржи и неконвертируемость

База маржи провайдера — сумма отправителя (`source_amount`): `margin = (fee_клиента − fee_провайдера) / source_amount`. Если сумму нельзя перевести в валюту лимита (нет пути в графе курсов), проверка не пропускается молча, а возвращает `RATE_UNAVAILABLE`: невидимый лимит опаснее честной ошибки. То же правило — для лимитов направления в `POST /quotes`: сумма в чужой валюте без пути конвертации даёт `RATE_UNAVAILABLE`, а не сравнение «как есть».

## A15. Порядок проверки вебхука

Сначала наличие секрета (`503`, если не настроен), затем подпись (`401`), и только потом поиск провайдера. Неизвестный провайдер с валидной подписью — `422 VALIDATION_ERROR`: провайдеры — серверный справочник, а не ввод клиента, отдельного кода для него нет.

## A16. Ключ идемпотентности — в пределах клиента

`UNIQUE(client_id, idempotency_key)`: два разных клиента вправе использовать одинаковые ключи. Поиск существующего перевода всегда идёт по паре (клиент, ключ).
