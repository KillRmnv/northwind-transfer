# Ревью: инфраструктура, конфигурация, БД, логирование, безопасность

Дата: 2026-11-19. Окружение проверки: Python 3.12, PostgreSQL 16.16 на `localhost:5433`, SQLite через `aiosqlite`, конфигурация из `.env`. Ссылки `файл:строка` — снимок рабочей копии на момент ревью; в каталоге есть параллельные несохранённые правки других сессий, поэтому номера строк могут сдвигаться. Код и тесты в рамках этого ревью не менялись.

Область: профили `postgres/mysql/sqlite` и типы (`GUID`, `Numeric(20,8)`, `DateTime(timezone=True)`), расхождения миграции и моделей, идемпотентность сидера и повторный запуск, утечки секретов в логи и ответы, служебные эндпоинты и Swagger, health/healthcheck, параметры PostgreSQL и пул, контейнерный lifecycle, гонки миграции и сидера при нескольких репликах.

## Подтверждённые баги

Ниже — только то, что воспроизведено на реальном коде/БД (команды выполнялись в рабочей копии, без правок репозитория). Базовый прогон suite в отдельной БД: `68 passed` — то есть перечисленные дефекты существующими тестами не ловятся.

1. **P0. Webhook без секрета принимает любую подпись и меняет деньги.** `Settings.provider_webhook_secret=""` по умолчанию, `verify_signature` при пустом секрете возвращает `True`, а `handle_webhook` пропускает проверку целиком. В дефолтном compose секрет публично известен (`local-dev-webhook-secret`). Любой, кто может дотянуться до `/webhooks/{provider}`, отправляет forged `FAILED` и запускает `run_attempts` (для `PENDING` это выплата, для `PROCESSING` — ретраи/ожидание), а forged `COMPLETED` завершает перевод, если провайдер подтверждает статус, и списывает резерв. Нарушение D10 («HMAC обязателен, несовпадение/отсутствие — 401»).

2. **P1. Гонка миграции двух реплик.** На свежей БД два параллельных `alembic upgrade head`: первый exit 0, второй exit 1 с `UniqueViolationError: duplicate key value violates unique constraint "pg_type_typname_nsp_index"` (второй прогон короче на 0.2 с). В `alembic/env.py` нет `pg_advisory_lock`/сериализации, поэтому масштабирование API на 2+ реплики ломает старт.

3. **P1. Гонка сидера двух реплик.** Два параллельных `python -m app.db.seed` на свежей БД: первый exit 0, второй exit 1 с `UniqueViolationError: duplicate key value violates unique constraint "currencies_pkey"`. `merge` не является upsert на уровне SQL. При `set -e` в entrypoint это падение контейнера; при отсутствии `restart:` API не поднимется.

4. **P1. Entrypoint не переживает недоступную БД.** `DB_HOST=127.0.0.1 DB_PORT=1 alembic upgrade head` завершается `ConnectionRefusedError` и `EXIT=1` сразу, без ретраев. `docker-compose.yml` не задаёт `restart:`, поэтому после рестарта/сбоя БД сервис остаётся лежать; `depends_on: service_healthy` действует только на первый запуск.

5. **P1. Сидер затирает операторские данные при каждом старте.** После seed выставлен `enabled=false` у провайдера, затем повторный seed: `enabled` снова `True`, при этом изменённый баланс сохранился (`500001.00`). Перезапуск контейнера откатывает ручные изменения комиссий/лимитов/флагов; балансы ведут себя иначе — семантика не задокументирована.

6. **P1. SQLite теряет точность `Numeric(20,8)`.** `Decimal("123456789012.12345678")` после round-trip = `Decimal("123456789012.12345886")`. Профиль, заявленный в D13 как «локальный быстрый прогон», не держит денежные инварианты D2; тесты на sqlite могут давать ложнозелёный/ложнокрасный результат.

7. **P1. SQLite/MySQL теряют timezone, окно обслуживания даёт 500.** `DateTime(timezone=True)` в SQLite возвращает naive `2026-01-01 12:00`; `w.from_at <= datetime.now(timezone.utc)` → `TypeError: can't compare offset-naive and offset-aware datetimes`. `in_maintenance` вызывается на каждом подборе провайдера, поэтому при наличии любого окна создание перевода на sqlite падает; для MySQL `DATETIME` аналогично не хранит tz.

8. **P1. Маскирование не покрывает `access_token`, `client_secret`, `session_id` и DSN.** Проверено: строки `GET /cb?access_token=SECRET1`, `GET /cb?client_secret=SECRET2`, `postgresql+asyncpg://transfer:SECRET3@db:5432/transfer`, `session_id=SECRET4` возвращаются из `redact_text` без изменений. `\b` не срабатывает после `_`, DSN userinfo не покрыт паттернами. Кейс 6 `logging-disclosure` («PROVIDER_WEBHOOK_SECRET, DSN, токены — нигде») не выполняется.

9. **P1. `pytest -n auto` не работает.** `pytest -n 2` на общей `transfer_test`: `sqlalchemy.exc.DBAPIError: deadlock detected ... DROP TABLE payout_attempts`, suite падает на setup (12 passed, 1 error до остановки; та же БД в это время может использоваться и другим прогоном). Изоляции БД/схемы по `PYTEST_XDIST_WORKER` нет, хотя `pytest-xdist` и требование `-n auto` есть в D14/SPEC.

10. **P1. Тесты не проверяют миграцию и индексы.** У всех таблиц `Base.metadata` список индексов пуст; миграция создаёт 9 индексов (`ix_quotes_direction`, `ix_transfers_client_created`, `ix_transfers_quote`, `ix_payout_attempts_*`, `ix_webhook_events_reference`, `ix_maintenance_windows_provider`, `ix_provider_directions_direction`, `ix_limit_definitions_client`). Фикстуры строят схему через `create_all`, поэтому ни один тест не выполняет `alembic upgrade` и не заметит дрейф прод-схемы.

11. **P1. Конкурентный одинаковый `Idempotency-Key` даёт 500.** Два параллельных `create_transfer` с ключом `same-key-race` на реальном PG: первый `created=True`, второй `IntegrityError: duplicate key value violates unique constraint "transfers_idempotency_key_key"`. В БД один перевод, `available=490000`, `reserved=10000` (деньги не задвоены), но контракт D8 «тот же ключ → тот же transfer_id» нарушен, клиент получает 500.

12. **P1. SQLite не проверяет внешние ключи.** `PRAGMA foreign_keys` = 0; вставка `Balance(client_id="ghost", currency="XXX")` успешна. На PG такой тест упадёт, на sqlite — нет; профиль не обеспечивает целостность D16/D17.

13. **P1. `SQLITE_PATH=:memory:` нерабочий.** При `NullPool` после `create_all` новый запрос открывает другое соединение и падает `OperationalError: no such table: currencies`. Конфигурация допускает этот путь без предупреждения.

14. **P1. Пароль с спецсимволами ломает DSN.** `DB_PASSWORD=p@ss/w:rd` → `make_url` разбирает host=`ss`, database=`w:rd@db:5432/transfer`; подключение уйдёт не туда. Пароль не URL-энкодится при сборке `database_url`.

15. **P1. Бюджет пула не согласован с `max_connections` при репликах.** `SHOW max_connections` = 100, PG-тюнинг применён (512MB/1536MB/16MB/…). При `pool_size=10`, `max_overflow=20` одна реплика занимает до 30 соединений; 4 реплики — 120 > 100, 3 реплики — 90 без запаса на миграции/админку. Валидации формулы D13 нет.
