## Подтверждённые баги (корень указан строкой, вывод — из кода, не из гипотез)

1. **P0, терминально-слепой `RETRY`** — `transfer_machine.py:78-85` не читает статус перевода;
   `transfers.py:349-351` безусловно продолжает цикл и POSTит. Самый тяжёлый класс раунда:
   новые выплаты на завершённых переводах.
2. **P0, реентерабельный `run_attempts`** — `transfers.py:295,304-307`: `attempt_no` из `len()` без
   UNIQUE в `tables.py:152-167`; параллельные драйверы (sync + вебхук-`FAILED` + сверка) дублируют
   попытки и выплаты. Phantom-запись покрывает только последовательный рестарт, не concurrency.
3. **P1, вечный `unresolved`** — `transfers.py:253-255` + `reconcile.py:55-64`: из состояния
   «попытка PROCESSING без `payout_id`» нет ребра наружу ни в одном драйвере; резерв висит вечно.
4. **P1, безусловный `completed++`** — `reconcile.py:89` выполняется и при `done is False`.
5. **P1, replay по протухшей котировке минтит новые payout** — `api/v1/transfers.py:90` всегда
   дёргает `run_attempts`; проверки `expires_at` внутри него нет (`transfers.py:249` только читает quote).
6. **P2, `CANCELLED` мёртв** — четыре ребра в `EDGES`, ноль акторов; тест `test_can_*` его не упоминает.

## Проверено, новых дефектов нет (чтобы не перепроверяли)

- Ядро `_settle`: `UPDATE … WHERE funds_settled=false AND status NOT IN (terminal)` + `rowcount==1`
  (`transfer_machine.py:94-104`) корректно сериализует `complete`-vs-`complete` и `complete`-vs-`fail`:
  проигравший возвращается без эффекта на баланс. Деньги через разные пути дважды не списываются.
