# balances-concurrency — резерв и параллельность

## Цель
Одна транзакция `создать перевод → FOR UPDATE строки баланса → проверить
доступно ≥ source+fee и лимиты → положить резерв` (D9). Параллельные заявки на
один баланс не дают двойного списания; дубли ключа ждут первую транзакцию.
Изоляция `READ COMMITTED` зафиксирована тестом, а не предположением.

## Источник в Java
- `service/concurrency.feature` (5 кейсов): 10/11/12 потоков по 100 USD против
  лимита 1000 (11 — граница блокировки; 10 ровно = не превышено); 50 потоков —
  все 50 строк, итог `5000`; 20 гоняющихся первых транзакций — ровно один fallback;
  два аккаунта — независимые прогоны; валюта без курса — без потерь.
- `service/limit_flag_scenario.feature`: `Concurrent posts for one client
  serialise on the limit row` (без блокировки 1 флаг вместо 2).
- `api/client_api.feature`: `Concurrent posts over HTTP all land` (20 запросов,
  ловит 3/3 — круглый запрос расширяет окно; держать рядом с сервисным).
- `TransactionIsolationTests` (3 кейса): `READ COMMITTED` держится;
  неподтверждённая строка/обновление невидимы другой транзакции (plain JDBC,
  детерминировано, не через `@Transactional`).

## Кейсы (вход → ожидание)

| # | Вход | Ожидание |
|---|------|----------|
| 1 | `SHOW transaction_isolation` | `read committed`, не `serializable` |
| 2 | Неподтверждённая вставка резерва | невидима второй транзакции; после коммита видна |
| 3 | Неподтверждённое обновление баланса | вторая читает старое значение |
| 4 | N параллельных `POST /transfers` на один баланс, сумма ≤ доступно | все созданы, `доступно + резерв + списано = старт` |
| 5 | N параллельных, сумма > доступно | часть `INSUFFICIENT_FUNDS`, перерасхода нет, итог сходится |
| 6 | Два разных клиента одновременно | независимые прогоны, блокировки не схлопываются |
| 7 | 50–100 конкурентных (`asyncio.gather`, `httpx`) | нет `TimeoutError` пула, `engine.pool.checkedout()` в пределах, все строки на месте |
| 8 | Дубли `Idempotency-Key` параллельно | один перевод (см. idempotency) |
| 9 | `GET /clients/{id}/balance` под нагрузкой | ключи `available`/`reserved` по каждой валюте (ищет `chaos_run.py`) |

## Адаптация под наш контракт
- Блокируем строку `balances` клиента по PK (`SELECT … FOR UPDATE`), а не строку
  лимита как в Java; порядок «есть что блокировать → читать итог» (D9, урок
  `TransactionService.applyFlag`).
- Финал: `COMPLETED` списывает резерв в расход, `FAILED`/`CANCELLED` возвращают
  в доступно — в той же транзакции что смена статуса.
- Честность как в Java: сервисные проверки вероятностны (окна планировщика),
  корректная реализация детерминирована; HTTP-сценарий держать рядом.
- Нагрузка: `pytest -n auto`, изоляция схем на воркер, `engine.dispose()`.
