# limits — суточные, скользящие и взвешенные лимиты

## Цель
Лимиты D11/A9: дефолт — суточный лимит клиента; окна — агрегацией по `transfers`
(`created_at >= now() − window`, полуоткрытое `[now−window, now)`), сравнение
строгое (`сумма > лимит`, остаток ноль — не превышение, урок Java
`domain-rules.md`); часовой пояс — UTC, одно место конверсии. Взвешенные категории:
вес решает правило, пишется на строку, задним числом не пересчитывается.

## Источник в Java
- `rule/limit_policies.feature` (7 кейсов): ровно-лимит — не превышено; past —
  превышено; взвешенная категория тратит половину; невзвешенная — полную;
  вес принадлежит правилу и пишется на строку; веса под monthly-sum правилом
  не читаются (читаются как 1 — намеренно, без смешивания половин).
- `WeightedLimitPolicyTests` (3 кейса): вес достигает строки (`service 0.5`,
  `product 1`); итог месяца суммируется взвешенным (800 как 400 + 600 как 300 =
  700, флаг решает по взвешенному, не по сырым 1400); каждая категория меряется
  против своего лимита, общий котёл запрещён.
- `service/limit_flag_scenario.feature`: остаток ровно ноль — не превышен;
  задним числом — против действующего на дату; новый лимит не обнуляет месяц
  (аналог: смена определения не пересчитывает прошлое).
- `api/request_validation.feature`: границы суммы лимита (тот же `@Digits(11,8)`).

## Кейсы (вход → ожидание)

| # | Вход | Ожидание |
|---|------|----------|
| 1 | Сумма окна ровно = лимит | не превышено (строгое `>`) |
| 2 | Сумма окна = лимит + 1 minor unit | `DAILY_LIMIT_EXCEEDED`, перевод не создаётся, резерв не висит |
| 3 | Окно 7/16 дней: перевод старше окна | не входит в сумму |
| 4 | Граница окна `[now−window, now)` | ровно `now−window` внутри/снаружи — один детерминированный вариант, зафиксирован |
| 5 | Часовой лимит (`HOURLY`) | превышение часа при целых сутках (дефолта `daily/6` нет — только явные записи) |
| 5b | Минутный лимит (`MINUTES`, окно в минутах из `window_days`) | работает как `HOURLY`, но окно короче; в примерах ТЗ не встречается |
| 6 | Лимит клиента в валюте ≠ валюте баланса (`c_003`: лимит USD, баланс RUB) | конвертация тем же курсом что quote |
| 7 | Взвешенная категория (`weight 0.5`) | в сумму окна входит `amount × weight` |
| 8 | Вес изменён после проводок | старые строки хранят старый вес, флаги не пересчитываются |
| 9 | Две категории | раздельные суммы, не общий котёл |
| 10 | Проверка внутри транзакции резерва | гонка двух заявок не обходит лимит (см. balances-concurrency) |
| 11 | `limit_definitions(client, scope, period)` дубль | `UNIQUE`, конфликт — не второй лимит |

## Адаптация под наш контракт
- Схема D11/D19: `limit_period_types` (`HOURLY, DAILY, WINDOW_N`, плюс `MINUTES`),
  `limit_definitions`, индексы `(client_id, created_at)`, `(client_id, category, created_at)`.
- `scope=category` зарезервирован, но не применяется: у перевода нет поля категории,
  такое правило молча пропускается (см. LIMITS L3).
- Месячного флага `limit_exceeded` из Java нет — не портировать truth table
  `limit_flag_rule` и `month_boundary` (см. README «не перенесено»);
  портируется только техника: строгое сравнение, ноль, заднее число, взвешенная сумма.
- Часовой пояс UTC, конверсия в одном limit-модуле (аналог `MonthBoundary`).

## Приоритет
**P1** (Level 3: суточный лимит; взвешенные/скользящие — глубина).
