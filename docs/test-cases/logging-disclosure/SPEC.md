# logging-disclosure — секреты не в логах

## Цель
В логах — метаданные, а не деньги клиента и не секреты деплоя. Проверяется
захватом реального вывода, а не чтением настроек.

## Источник в Java
- `LoggingDisclosureTests` (7 кейсов): отказ провайдера не несёт API-ключ
  (`SafeLog.failure` режет `apikey/token`, но оставляет `time_series`+`404`);
  `SafeLog.scrub` режет где бы ни встретилось; счёт маскируется (`******0462`,
  `null → ***`); адрес — только последний октет (`***.***.***.77`); timestamp сам
  по себе безопасен и не трогается; счёт из запроса никогда не пишется целиком.
- `HttpLoggingDisclosureTests` (2 кейса): тела запроса/ответа выключены на фильтре
  (усечённое тело — всё равно тело); адрес заменён, а не сконфигурирован; в строке
  есть метод/путь/порт для корреляции, но нет `127.0.0.1` целиком.

## Кейсы (вход → ожидание)

| # | Вход | Ожидание |
|---|------|----------|
| 1 | Ошибка провайдера с ключом в URL | в логе нет секрета, есть символ/код для отладки |
| 2 | Строка с `apikey=/token=` где угодно | значение вырезано скруббером |
| 3 | Счёт/имя получателя в запросе | в логе только маска (последние 4), полного нет |
| 4 | IP вызывающего | только последний октет |
| 5 | HTTP-лог запроса/ответа | метод + путь + статус + `transfer_id`, без тел |
| 6 | `PROVIDER_WEBHOOK_SECRET`, DSN, токены | нигде в логах/метриках/ответах (D12: `docs/openapi.json` только dev) |
| 7 | Валидный timestamp/UUID в сообщении | не уродуется скруббером (защита от переусердствования) |

## Адаптация под наш контракт
- Структурные логи Level 4 — с `transfer_id`, без PII; тела вебхуков не логируем.
- `/env`, `/.env`, `/actuator`, `/metrics`, `/info` отсутствуют (D12).
- Проверка — `caplog`/перехват handler'а на реальном кодовом пути, характерные
  значения (`c_003`, `prov_alpha`, заведомо ложный секрет).

## Приоритет
**P1** (защита, провал = провал ревью).
