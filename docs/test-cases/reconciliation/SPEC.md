# reconciliation — сверка и неизвестный итог

## Цель
Ни одной двойной выплаты и ни одного зависшего резерва: каждый перевод либо в
терминале, либо в явном «требует проверки». Ответ не пришёл ≠ можно идти дальше:
сначала `GET ?reference=`, одиночный `GET` итогом не считается.

## Источник в Java
- `service/daily_rate_sweep.feature`: свип пишет день, который спросит транзакция
  (`2026-10-09`, а не `2026-10-10`/`2026-10-01`); строка, которую никто не читает, —
  потерянный вызов; непокрытый день всё равно стоит вызов.
- `service/currency_sweep.feature`: стартовый импорт = тот же импорт, идемпотентен;
  недоступный провайдер стоит только импорта.
- `service/conversion_boundaries.feature`: `A provider that is down does not cost
  the transaction`; `A stored rate is found without asking the provider at all`.
- `api/rates_fallback.feature`: `source` называет ответившего (`stored rate names
  "frankfurter" as its source`).
- Урок `test-cases.md §Чегo в наборе нет`: `findLatestOnOrBefore` без `limit 1`
  на длинной истории — держать историю сверки ограниченной окном.

## Кейсы (вход → ожидание)

| # | Вход | Ожидание |
|---|------|----------|
| 1 | Ответ не пришёл (обрыв/таймаут/`504` после отправки) | `PROCESSING` + «требует проверки», деньги в резерве; клиент видит статус, не `FAILED` |
| 2 | `GET ?reference=` записи не находит | можно к следующему провайдеру (`DROP_LOST`-аналог) |
| 3 | `GET ?reference=` находит запись | привязать попытку к ней, ждать/сверить, второго платежа нет |
| 4 | `visibility_lag` 3–15 с (свежая выплата — `404`) | поллинг с повторами, `404` сразу после отправки — не «нет записи» |
| 5 | `stale_read` 1–3 с (`GET` врёт `PROCESSING` после settle) | сходимость: N совпадающих чтений, одиночный `GET` итогом не считается |
| 6 | Процесс упал между «отправили» и «записали» | после рестарта фоновая сверка доводит до терминала по `reference` |
| 7 | Джоб сверки по висящим `PROCESSING` (каждые N минут) | сверяет `GET payouts` с `admin/ledger`, доводит до терминала; single-runner (`FOR UPDATE SKIP LOCKED`) |
| 8 | Два воркера сверки одновременно | одна и та же выплата обрабатывается один раз |
| 9 | `chaos_run.py --transfers 300` | ноль двойных выплат (сверка с ledger мока), ноль зависших резервов |
| 10 | Попытка записана с `source` ответившего | `GET /transfers/{id}` показывает кто/когда/с каким результатом |

## Адаптация под наш контракт
- Индекс `(reference)` на `payout_attempts` под сверку/вебхуки (D19).
- Админ-ручки мока (`/admin/ledger`, `?reference=`) — только в тестах/сверке,
  у реальных провайдеров их нет.
- Период сверки и число сходящихся чтений — в DECISIONS при реализации (A10).

## Приоритет
**P0** (кейсы 1–6, 9; Level 3), остальное **P1**.
