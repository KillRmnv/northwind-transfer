# idempotency — ключ идемпотентности

## Цель
Повтор того же запроса не создаёт второй перевод (D8/A4). Ключ + хеш тела,
`UNIQUE` в той же транзакции что резерв. Тот же ключ с другим телом — `422`,
а не молчаливое игнорирование и не второй перевод.

## Источник в Java
- Прямого аналога нет (в Java идемпотентности переводов не было); техника взята из:
  `service/concurrency.feature` (гонка за создание fallback-лимита — ровно один),
  `TransactionIsolationTests` (UNIQUE + блокировка как вторая линия обороны),
  `service/currency_sweep.feature` (`startup import is idempotent`, повтор не дублирует).
- Поведение мока (starter-notes): тот же ключ + другое тело → `409
  IDEMPOTENCY_KEY_REUSED`; тот же ключ + то же тело → повтор ответа.

## Кейсы (вход → ожидание)

| # | Вход | Ожидание |
|---|------|----------|
| 1 | Повтор `POST /transfers` с тем же ключом и телом до выполнения | тот же `transfer_id`, второй перевод не создан |
| 2 | Повтор во время выполнения (`PROCESSING`) | тот же `transfer_id`, текущий статус |
| 3 | Повтор после терминала (`COMPLETED/FAILED`) | тот же `transfer_id`, терминальный статус |
| 4 | Тот же ключ + другое тело (`quote_id/amount/recipient`) | `422 IDEMPOTENCY_CONFLICT`, второй перевод не создан |
| 5 | Два параллельных запроса с одним ключом | один перевод, второй упирается в `UNIQUE` и ждёт первую транзакцию |
| 6 | Повтор `POST /{provider}/payouts` с тем же `reference` | маппинг `409` мока → наш `transfer_id`, двойной выплаты нет |
| 7 | Рестарт между «отправили» и «записали» | после рестарта повтор с тем же ключом возвращает исходный перевод (см. reconciliation) |

## Адаптация под наш контракт
- Заголовок `Idempotency-Key` на `POST /transfers` и на вызовах мока (`reference`
  как наш id).
- Хранить хеш тела рядом с ключом; сравнение — константное по длине.
- `UNIQUE(idempotency_key)` (D19) — вторая линия после проверки в сервисе.
- Chaos-проверка: `available + reserved + списанное = старт` (Level 2),
