# quote-contract — контракт POST /quotes

## Цель
Поля запроса/ответа именованы по контракту Backend §6, лимиты направления,
способы выплаты и оба режима `SOURCE`/`TARGET` проверяются границами (BVA) и
классами (EP). Валидный граничный запрос реально сохраняется, а не только принимается.

## Источник в Java
- `rule/wire_contract.feature`: шесть имён запроса, три добавленных поля ответа,
  `400` называет поле так, как его пишет клиент (snake_case).
- `api/request_validation.feature` (11 кейсов): границы `@DecimalMin`/`@Digits(11,8)`,
  счёт ровно 10 цифр, код ровно 3 буквы, CHECK `> 1990`, обязательные поля
  (`missing/blank` — один класс), не-JSON → `400`, без `Content-Type` → `415`,
  граничное валидное значение реально записано.
- `rule/ledger_policy.feature`: границы длины кода, пустой код, шкала `0/2/4`,
  потолок хранения.

## Кейсы (вход → ожидание)

| # | Вход | Ожидание |
|---|------|----------|
| 1 | Имена полей `POST /quotes` по §6 | точное соответствие, лишний компонент = смена контракта |
| 2 | Ответ `201` содержит `quote_id, direction_id, source_amount, fee, amount_to_convert, rate, target_amount, breakdown, expires_at` | все поля, деньги — строки по `minor_units` |
| 3 | `amount` на границах min/max направления (min−ε, min, max, max+ε) | ниже → `AMOUNT_BELOW_MIN`, выше → `AMOUNT_ABOVE_MAX` |
| 4 | Нет направления / способа выплаты | `UNSUPPORTED_DIRECTION` |
| 5 | `amount_type=TARGET` | инверсия D3, сверка прямым прогоном SOURCE (examples #1↔#3) |
| 6 | TARGET с округлением в 1 minor unit | детерминированное правило «округление последней операции вверх» (A2) |
| 7 | `charged_in=TARGET` (RU-VN-BANK, KW-JP-BANK) | комиссия в валюте получателя, пересчёт явным шагом в `breakdown` |
| 8 | Минимальная комиссия (`min`) | срабатывает минимум (пример §9 #2: 2000 RUB → 50 RUB) |
| 9 | Тело не JSON / без `Content-Type` | `VALIDATION_ERROR` (`400` / `415`) |
| 10 | Отсутствующее/пустое/пробельное обязательное поле | `VALIDATION_ERROR`, `details` называет поле в нотации запроса |
| 11 | Граничный валидный запрос | `201` + строка реально сохранена, `GET /quotes/{id}` её отдаёт |
| 12 | Котировка старше `quote_ttl_sec` | `QUOTE_EXPIRED`; неизвестный id → `QUOTE_NOT_FOUND` |

## Адаптация под наш контракт
- Пути: `POST /quotes`, `GET /quotes/{id}` (+ корневые дубли по SPEC).
- `sum`-границы Java (`@Digits(11,8)`, 12 целых → `400`) заменить границами
  `amount_limits` тарифа + строгость `amount_is_valid` мока по `minor_units`.
- Счёт из 10 цифр и `expense_category` у нас отсутствуют — не портировать.
- `breakdown` — свободная форма, но шаги проверяются soft assertions (`pytest-check`).
- Детерминизм: один вход → один расчёт (повтор `POST /quotes` с тем же телом
  даёт тот же расчёт, новый `quote_id` допустим).
