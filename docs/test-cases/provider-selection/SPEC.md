# provider-selection — выбор и фолбэк провайдеров

## Цель
Жёсткий фильтр → маржа → взвешенный скоринг → fallback (D7). Неизвестный итог —
не fallback, а проверка `GET ?reference=` (иначе двойная выплата и провал chaos_run).

## Источник в Java
- `api/rates_fallback.feature` (8 кейсов): запасной отвечает когда у платного
  пусто/недоступен; платный спрашивается первым; запасной — в той же ориентации;
  ни у кого нет — не ошибка; транзакция старше бесплатного тира всё равно оценена;
  список валют — у кого есть.
- `rule/rate_fetch_coordination.feature` (3 кейса): два звонящих на одну пару/день —
  один вызов; та же пара наоборот — один вызов + инверсия на выходе 12 знаков;
  присоединившийся получает ответ в своей ориентации.
- `api/client_api.feature`: `A pair the provider publishes the other way round
  is converted by division`; `A pair the provider does not publish in either
  direction is stored without a flag`; батч `asks the provider once for a pair`
  (координатор схлопывает только пока вызов в полёте — провайдер делается медленным).
- `WeightedLimitPolicyTests` + `rule/limit_policies.feature`: взвешивание решает
  правило, а не вызывающий; вес пишется на строку (аналог: скоринг/маржа пишется
  в попытку и историю, задним числом не пересчитывается).

## Кейсы (вход → ожидание)

| # | Вход | Ожидание |
|---|------|----------|
| 1 | Несколько подходящих провайдеров | выбран max `score = w1·margin − w2·latency + w3·success_rate` (веса фиксированы в DECISIONS при реализации) |
| 2 | `decline (422)` у первого | сразу следующий, без проверки ledger |
| 3 | `5xx` без созданной записи | следующий с записью попытки |
| 4 | Обрыв / таймаут / `504` после отправки (`DROP_CREATED, HANG_CREATED, ERROR_CREATED`) | сначала `GET ?reference=`; записи нет → следующий; запись есть → привязать и ждать/сверить |
| 5 | `slow` 30 с | ждать до таймаута D5, дальше `202 PROCESSING` + поллинг, не `FAILED` |
| 6 | Никто не проходит по `min_margin_percent` | `FAILED`, резерв возвращён; взятие ниже минимума — только с пометкой в истории (A6) |
| 7 | `prov_delta` (`enabled=false`), `prov_echo` в окне обслуживания | отфильтрованы до скоринга |
| 8 | Сумма в валюте провайдера вне min/max | отфильтрован (наш фильтр строже ±10% мока — норма, starter-notes) |
| 9 | Курса нет нигде (`KZ-TH-BANK`) | `RATE_UNAVAILABLE`, перевод не создаётся |
| 10 | Прямой пары нет, обратная есть | кросс/инверсия тем же курсом что quote (12 знаков, округление один раз) |
| 11 | Два параллельных перевода — одна пара/день | один вызов rates (координация в полёте, тест с медленным провайдером) |
| 12 | `MOCK_MODE=chaos`, все сценарии `X-Scenario` | `ok/decline/error_5xx/slow` доходят до терминала |

## Адаптация под наш контракт
- Цепочка `Direction→Limits→Availability→Margin→Scoring→AttemptExecutor` (D7),
  каждый хендлер — отдельный класс, `respx`-тесты позменно.
- Валюта провайдера ≠ валюте перевода: конвертация лимитов/комиссий тем же
  курсом, кросс через промежуточную (`reference_data.convert`).
- `currency_rate.source` называет ответившего (урок Java assumptions §2).
- История `GET /transfers/{id}`: кто, когда, с каким результатом + «почему этот»
  (Level 4).
